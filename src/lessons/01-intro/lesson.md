## Адрес сайта

У каждой страницы в вебе есть адрес — [[URL]]. Он читается слева направо: как связаться, с каким сервером, какую страницу открыть.

:::shot img/intro-url.webp
Пять частей адреса. Обязательны только протокол и домен
:::

- **[[Протокол]]** — правила общения. `https` — то же, что `http`, но с шифрованием.
- **[[Домен]]** — имя сервера. Людям удобны имена, компьютерам — числа, поэтому домен переводят в [[IP-адрес]].
- **Путь** — какую страницу или файл отдать.
- **Параметры** — после `?`, пары `имя=значение` через `&`: `?q=кофе&page=2`.
- **Якорь** — после `#`, место на странице. Браузер прокручивает к нему сам, на сервер он не уходит.

:::tip Где увидеть полный адрес
Chrome прячет `https://` в адресной строке. Щёлкните по адресу — появится целиком.
:::

## Что происходит, когда вы открываете сайт

Вы вводите `https://shop.ru` и нажимаете Enter. Страница появляется через полсекунды, но за это время происходит семь шагов.

:::diagram id=request
type: sequence
actors:
  - {id: b, title: Браузер, kind: front}
  - {id: dns, title: DNS-сервер, text: «телефонная книга», icon: book}
  - {id: s, title: Сервер shop.ru, text: 185.12.3.4, kind: back}
messages:
  - {note: "Ввели `https://shop.ru`", at: b, kind: front, step: 1}
  - {from: b, to: dns, label: Какой IP у shop.ru?, step: 2}
  - {from: dns, to: b, label: "`185.12.3.4`", dashed: true, step: 2}
  - {from: b, to: s, both: true, label: Соединение и шифрование (TLS), step: 3}
  - {from: b, to: s, label: Запрос, code: GET / HTTP/1.1, kind: front, step: 4}
  - {from: s, to: b, label: Ответ, code: 200 OK + HTML, kind: back, step: 5}
  - {from: s, to: b, label: Файлы из HTML, code: "style.css, app.js, logo.png", kind: back, step: 6}
  - {note: Страница на экране, at: b, kind: front, step: 7}
steps:
  - Вы вводите [[URL]] и нажимаете Enter. Браузер знает только имя — [[домен]] `shop.ru`.
  - Компьютеры находят друг друга по числам. Браузер спрашивает у [[DNS]]: «Какой [[IP-адрес]] у shop.ru?» — и получает `185.12.3.4`.
  - Браузер соединяется с сервером и договаривается о шифровании. Это буква S в [[HTTPS]] и замок в адресной строке.
  - "Браузер отправляет [[HTTP]]-запрос: «`GET /` — дай главную страницу»."
  - Сервер отвечает [[статус-код|статус-кодом]] `200 OK` и присылает HTML-документ.
  - В HTML есть ссылки на стили, скрипты и картинки. Браузер скачивает каждый файл отдельным запросом.
  - Браузер собирает всё вместе и рисует страницу. Дальше JavaScript реагирует на ваши клики.
:::

## Запрос и ответ

Браузер и сервер обмениваются обычным текстом. Так выглядят запрос и ответ, если убрать всё лишнее:

:::cols
```http
GET /catalog HTTP/1.1
Host: shop.ru
```
+++
```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8

<!doctype html>
<html>…страница…</html>
```
:::

Первая строка запроса — [[метод HTTP|метод]] и путь. Метод говорит, что сделать:

| Метод | Что делает | Пример |
|---|---|---|
| `GET` | Получить | открыть каталог, загрузить список задач |
| `POST` | Создать | оформить заказ, отправить сообщение |
| `PUT`, `PATCH` | Изменить | поменять адрес доставки |
| `DELETE` | Удалить | удалить комментарий |

Первая строка ответа — [[статус-код]]. По первой цифре понятно, что случилось:

| Код | Значит | Частые примеры |
|---|---|---|
| `2xx` | Всё получилось | `200 OK`, `201 Created` — создано |
| `3xx` | Ищите в другом месте | `301` — страница переехала |
| `4xx` | Ошибка в запросе | `404` — не найдено, `401` — нужно войти, `403` — нельзя |
| `5xx` | Ошибка на сервере | `500` — сервер упал |

`4xx` — виноват клиент: опечатка в адресе, нет прав. `5xx` — виноват сервер. Фронтенд должен показать понятное сообщение в обоих случаях. Подробно HTTP разберём в уроке {{n:http}}.

:::tip Проверьте сами
В конце урока вы откроете вкладку Network и увидите эти запросы на реальном сайте. Обычно их 50–150 на одну страницу.
:::

## Клиент и сервер

[[Клиент]] спрашивает, [[сервер]] отвечает. Эта схема называется **клиент-серверной архитектурой**. На ней построен почти весь веб.

:::diagram id=client-server
type: flow
caption: Один сервер обслуживает сайт, мобильное приложение и другие сервисы
items:
  - group: Клиенты
    kind: front
    items:
      - {title: Сайт в браузере, text: ноутбук}
      - {title: Мобильное приложение, text: телефон}
      - {title: Другой сервис, text: "например, банк"}
  - {arrow: pair, label: запросы, back: ответы}
  - {title: Сервер, text: "проверяет права, считает, сохраняет", code: api.shop.ru, kind: back}
  - {arrow: both}
  - {title: База данных, text: "товары, заказы, пользователи", kind: db}
:::

Три свойства, которые важно запомнить:

1. **Клиентов много, сервер один.** Сайт и мобильное приложение банка ходят в один и тот же бэкенд.
2. **Данные живут на сервере.** Поэтому в почте с телефона и с ноутбука одни и те же письма.
3. **Клиенту нельзя доверять.** Код фронтенда скачивается к пользователю, и тот может его изменить. Поэтому цены, права и остатки проверяет бэкенд.

:::mistake «Спрячу кнопку — и никто не удалит чужой заказ»
Скрытая кнопка защищает только от случайного клика. Пользователь откроет DevTools и отправит запрос сам. Проверка «можно ли этому пользователю удалить заказ» всегда делается на сервере.
:::

## API — договор между фронтом и бэком

Фронтенд и бэкенд часто пишут разные люди. Чтобы они не мешали друг другу, заранее договариваются: какие адреса есть на сервере, что туда отправлять и что придёт в ответ. Такой договор называется [[API]].

:::diagram id=api
type: flow
caption: Фронтенд просит список задач, бэкенд отвечает данными в JSON
items:
  - {title: Фронтенд, text: показывает список задач, kind: front}
  - {arrow: pair, label: "Запрос: `GET /tasks`", back: "Ответ: `200` и JSON"}
  - {title: Бэкенд, text: достаёт задачи из базы, kind: back}
:::

Ответ приходит в формате [[JSON]] — это текст, похожий на объекты JavaScript:

```json
[
  { "id": 1, "title": "Купить молоко", "done": false },
  { "id": 2, "title": "Сдать урок 1", "done": true }
]
```

Фронтенд получает эти данные и сам решает, как их показать: списком, таблицей, карточками. Бэкенду всё равно, как выглядит интерфейс. Фронтенду всё равно, в какой базе лежат задачи. Это разделение позволяет двум командам работать параллельно. Как устроены HTTP и JSON, подробно разберём в уроке {{n:http}}.

## Что делает фронтенд-разработчик

Дизайнер рисует экран. Фронтенд-разработчик делает так, чтобы экран работал у настоящих людей:

- **Вёрстка по макету** — страница выглядит как в Figma, на телефоне и на ноутбуке.
- **Поведение** — кнопки, формы, фильтры, всплывающие окна.
- **Данные с сервера** — запросить, показать, обработать ошибку.
- **Доступность** — сайтом можно пользоваться с клавиатуры и программой экранного доступа.
- **Скорость** — страница открывается быстро даже на слабом телефоне.

Макет обычно показывает один экран — с данными. А у каждого экрана минимум четыре состояния, и все четыре — работа фронтенда:

:::shot img/intro-states.webp
Один экран «Мои заказы»: пока данные грузятся, когда их нет, когда сервер не ответил и когда всё хорошо
:::

## Кто есть кто в команде

| Роль | Что делает | Инструменты | Результат |
|---|---|---|---|
| **[[Фронтенд]]-разработчик** | Интерфейс: вёрстка, логика экранов, запросы к API | HTML, CSS, JS, TypeScript, React | Работающие экраны в браузере |
| **[[Бэкенд]]-разработчик** | Логика сервера, API, хранение данных | Node.js, Python, Go, Java, SQL | API и база данных |
| **[[Фулстек]]-разработчик** | И то, и другое, обычно в небольших проектах | Всё выше | Фича целиком |
| **Мобильный разработчик** | Приложения для iOS и Android | Swift, Kotlin, React Native | Приложение в сторе |
| **Дизайнер** | Как выглядит и как работает интерфейс | Figma | Макеты экранов |
| **Аналитик** | Что именно нужно сделать, какие правила | Документы, схемы, SQL | Требования и задачи |
| **[[QA]] (тестировщик)** | Ищет баги до пользователей | Чек-листы, автотесты | Отчёты о багах |
| **[[DevOps]]** | Серверы, выкладка, мониторинг | Linux, Docker, облака | Приложение стабильно работает |
| **Менеджер продукта** | Решает, что делать в первую очередь и зачем | Трекеры задач, метрики | План и приоритеты |

Путь одной фичи, например кнопки «Добавить в избранное»:

1. Менеджер решает, что фича нужна. Аналитик описывает правила: сколько товаров можно добавить, что видит гость без аккаунта.
2. Дизайнер рисует кнопку и её состояния в Figma.
3. Бэкенд делает адрес API `POST /favorites`, фронтенд — кнопку, которая туда отправляет запрос.
4. QA проверяет, DevOps выкладывает новую версию. Это называется [[деплой]].

## Где рождается страница: MPA, SPA, SSR

Главный архитектурный вопрос для фронтенда: кто собирает HTML — сервер или браузер. Есть три подхода.

:::diagram id=mpa-spa-ssr
type: rows
caption: Три способа доставить страницу пользователю
rows:
  - label: MPA
    sub: многостраничное
    items:
      - {title: Клик по ссылке, icon: false}
      - {arrow: right}
      - {title: Сервер собирает, text: новую HTML-страницу, kind: back}
      - {arrow: right}
      - {title: Страница, text: загружается целиком, kind: front}
    note: "Примеры: Википедия, блоги, сайты компаний"
  - label: SPA
    sub: одностраничное
    items:
      - {title: Первый вход, text: пустой HTML + JS, icon: false}
      - {arrow: right}
      - {title: Дальше сервер, text: отдаёт только JSON, kind: back}
      - {arrow: right}
      - {title: JS перерисовывает, text: нужную часть экрана, kind: front}
    note: "Примеры: Gmail, Figma, личные кабинеты. Так работает React"
  - label: SSR
    sub: рендер на сервере
    items:
      - {title: Запрос страницы, icon: false}
      - {arrow: right}
      - {title: Сервер запускает React, text: и отдаёт готовый HTML, kind: back}
      - {arrow: right}
      - {title: JS «оживляет» страницу, text: дальше как SPA, kind: front}
    note: "Примеры: интернет-магазины и медиа на Next.js, где важны скорость и поиск"
:::

- **[[MPA]]** — классика. Каждая ссылка загружает новую страницу целиком. Просто и надёжно, но при каждом переходе экран «моргает».
- **[[SPA]]** — приложение загружается один раз. Дальше JavaScript сам меняет экран, а с сервера берёт только данные в JSON. Работает быстро, как настольная программа.
- **[[SSR]]** — гибрид. Сервер присылает готовый HTML (быстро показать и хорошо для поисковиков), потом страница работает как SPA.

В курсе вы будете делать **SPA на React**: сейчас это самый частый формат в вакансиях. SSR (фреймворк Next.js) — логичный следующий шаг после курса.

## Монолит и микросервисы

Это про устройство бэкенда. Фронтенду достаточно знать слова, чтобы понимать разговоры в команде.

:::diagram id=monolith
type: rows
caption: Один большой сервис или много маленьких

    sub: одно приложение
    items:
      - group: Бэкенд

          - {title: Заказы}
          - {title: Оплата}
          - {title: Доставка}
      - {arrow: both}
      - {title: Одна база данных, kind: db}
    note: Проще начать. Когда проект растёт, его тяжело менять.
  - label: Микросервисы
    sub: много сервисов
    items:
      - {title: Пользователи, text: своя база, kind: back}
      - {title: Заказы, text: своя база, kind: back}
      - {title: Оплата, text: своя база, kind: back}
      - {title: Доставка, text: своя база, kind: back}
    note: Команды работают и выкладывают сервисы независимо. Сложнее в поддержке.

- **[[Монолит]]** — весь бэкенд в одном приложении. Так начинают почти все проекты.
- **[[Микросервисы]]** — бэкенд разбит на сервисы: пользователи, заказы, оплата. Их делают разные команды и выкладывают независимо.

Для фронтенда разницы почти нет: в обоих случаях бэкенд — это набор адресов API.

## HTML, CSS и JavaScript

Браузер понимает три языка. У каждого своя задача:

:::cols
**[[HTML]] — структура.** Что есть на странице.

```html
<button>Купить</button>
```
+++
**[[CSS]] — внешний вид.** Как это выглядит.

```css
button { background: purple; }
```
+++
**[[JavaScript]] — поведение.** Что происходит при действиях.

```js
button.onclick = () => alert('Готово');
```
:::

Попробуйте сами. Код слева можно менять — результат справа обновится сразу.

:::sandbox Три языка одной кнопки height=320
```html
<h2>Кофе с собой</h2>
<p>Цена: <b id="price">250</b> ₽</p>
<button id="buy">Купить</button>
```
```css
button {
  background: rebeccapurple;
  color: white;
  border: 0;
  padding: 10px 20px;
  border-radius: 8px;
  font-size: 16px;
}
```
```js
const button = document.querySelector('#buy');
button.addEventListener('click', () => {
  button.textContent = 'В корзине ✓';
  console.log('Кофе добавлен в корзину');
});
```
:::

Три эксперимента:

1. На вкладке CSS замените `rebeccapurple` на `tomato`.
2. Удалите весь CSS. Кнопка стала серой, но работает — структура и поведение на месте.
3. Верните CSS (кнопка «Сбросить») и удалите весь JavaScript. Кнопка красивая, но клик ничего не делает.

## Браузеры

Браузеров много, а движков, которые рисуют страницы, — три. Код, который работает в одном браузере, почти всегда работает и в других, но проверять нужно.

| Движок | Браузеры | Где важен |
|---|---|---|
| Chromium (Blink) | Chrome, Edge, Opera, Яндекс Браузер | больше половины пользователей |
| WebKit | Safari | все браузеры на iPhone, стандартный на Mac |
| Gecko | Firefox | небольшая доля, но свои особенности |

На курсе разрабатываем в Chrome — у него самые удобные инструменты. Готовую работу открываем ещё и в Safari: он уже есть на Mac.

## Кем вы станете после курса

В вакансиях разработчиков делят по уровням. После курса вы — junior: знаете основу и делаете задачи сами, со старшим коллегой рядом.

| Уровень | Опыт | Как работает |
|---|---|---|
| **Junior** | до 1–2 лет | делает понятные задачи, спрашивает, учится на ревью |
| **Middle** | 2–4 года | делает фичу целиком сам, помогает джунам |
| **Senior** | от 4–5 лет | решает, как устроить систему, отвечает за качество |

Годы — ориентир, а не правило. Уровень определяют задачи, которые вы решаете без помощи. Как искать первую работу, разберём в уроке {{n:deploy-career}}.

## Как учиться на курсе

Каждый урок проходит по одному циклу:

1. **Текст урока** — читать с открытым редактором, повторять примеры. Около 1 часа.
2. **Слайды** — занятие с ментором: разбор, вопросы, живой код.
3. **Квиз** — 5 минут, проверка, что главное усвоено.
4. **Задания** — от лёгкого к сложному. Застряли больше чем на 30 минут — пишите ментору.
5. **Ревью** — ментор проверяет задания по чек-листу. До урока {{n:git-basics}} работы сдаются файлом, потом — через GitHub.

Хороший вопрос ментору экономит час переписки:

```text
Что делаю: задание 2 урока {{n:css-basics}}, пытаюсь покрасить кнопку.
Что ожидаю: кнопка станет фиолетовой.
Что получаю: кнопка осталась серой. Скриншот и код приложил.
Что уже попробовал: проверил, что файл style.css подключён. Во вкладке Elements стиля нет.
```

:::note Правила работы с AI-ассистентами
AI (ChatGPT, Claude и другие) — отличный репетитор и плохой решатель домашек.
- **Можно:** попросить объяснить непонятное, дать подсказку без решения, найти ошибку в вашем коде и объяснить её.
- **Нельзя:** генерировать решение задания целиком. Вы получите зачёт, но не навык, и это вскроется на собеседовании.
- **Правило:** каждую строку сданного кода вы должны уметь объяснить ментору.

Как работать с AI в реальных проектах, разберём в уроке {{n:deploy-career}}.
:::

## Частые заблуждения

:::mistake «Фронтенд — это чтобы было красиво»
Красиво делает дизайнер. Фронтенд отвечает за то, чтобы интерфейс работал: загружал данные, обрабатывал ошибки, был быстрым и удобным на любом экране.
:::

:::mistake «Сайт хранится у меня в браузере»
В браузере — только копия интерфейса. Данные лежат на сервере, поэтому они одинаковые на всех устройствах.
:::

:::mistake «Без математики и английского в программирование не попасть»
Для фронтенда хватает школьной арифметики. Английский нужен на уровне «читаю документацию с переводчиком» — он подтянется сам, названия в коде английские.
:::

:::mistake «Надо сначала выучить всё про HTML, потом переходить к CSS»
Никто не знает всё. Профессионалы постоянно читают документацию. Цель — понимать, как устроено, и уметь быстро найти детали.
:::

## Шпаргалка

| Понятие | Одной строкой |
|---|---|
| Фронтенд | Интерфейс в браузере: HTML + CSS + JS |
| Бэкенд | Логика и данные на сервере |
| API | Договор: какие запросы можно отправить и что придёт в ответ |
| URL | Протокол + домен + путь + `?параметры` + `#якорь` |
| HTTP | Протокол запросов и ответов |
| Методы | `GET` получить, `POST` создать, `PUT`/`PATCH` изменить, `DELETE` удалить |
| Статус-коды | `2xx` успех, `3xx` переезд, `4xx` ошибка клиента, `5xx` ошибка сервера |
| JSON | Текстовый формат данных |
| DNS | Домен → IP-адрес |
| SPA | Загружается один раз, дальше меняет экран сам |
| DevTools | ⌥⌘I: Elements — HTML, Network — запросы |

## Квиз

:::quiz
- q: Где выполняется код фронтенда?
  options:
    - На сервере компании
    - В браузере пользователя
    - В базе данных
    - На DNS-сервере
  answer: 1
  why: Код фронтенда скачивается к пользователю и выполняется в его браузере. Поэтому его можно посмотреть и изменить.
- q: Что делает DNS?
  options:
    - Шифрует соединение
    - Хранит HTML-страницы сайта
    - Переводит доменное имя в IP-адрес
    - Проверяет, есть ли у пользователя доступ
  answer: 2
  why: 'DNS — «телефонная книга»: по имени `shop.ru` находит адрес `185.12.3.4`. Шифрование — это TLS, буква S в HTTPS.'
- q: 'Какая часть адреса `https://shop.ru/catalog?sort=price#reviews` не уходит на сервер?'
  options:
    - "`shop.ru`"
    - "`/catalog`"
    - "`?sort=price`"
    - "`#reviews`"
  answer: 3
  why: Якорь после решётки нужен только браузеру — чтобы прокрутить к месту на странице. Путь и параметры сервер получает.
- q: Сервер ответил `404`. Что это значит?
  options:
    - Всё хорошо
    - Сервер упал
    - Такой страницы нет — ошибка в запросе
    - Нужно подождать
  answer: 2
  why: 4xx — ошибка на стороне клиента, 404 — «не найдено». Если бы сервер упал, был бы 5xx, например 500.
- q: Пользователь через DevTools показал скрытую кнопку «Скидка 90%» и нажал её. Что должно защитить магазин?
  options:
    - То, что кнопка была скрыта
    - Проверка на бэкенде, может ли этот пользователь получить скидку
    - HTTPS
    - Сложный для чтения код фронтенда
  answer: 1
  why: Клиенту нельзя доверять. Всё в браузере пользователь может изменить. Права и цены проверяет сервер.
- q: Что такое API в веб-разработке?
  options:
    - Язык программирования для серверов
    - Договор о том, какие запросы можно отправить серверу и что он ответит
    - Библиотека для красивых кнопок
    - Программа для хранения данных
  answer: 1
  why: API — это интерфейс между программами. Например, `GET /tasks` возвращает список задач в JSON.
- q: Чем SPA отличается от MPA?
  options:
    - SPA работает без интернета
    - В SPA нет HTML
    - SPA загружается один раз, а дальше получает только данные и сам перерисовывает экран
    - SPA можно сделать только на сервере
  answer: 2
  why: В MPA каждый переход — новая HTML-страница с сервера. В SPA JavaScript меняет экран без перезагрузки.
- q: На странице кнопка есть и работает, но выглядит как серый прямоугольник. Какой части не хватает?
  options:
    - HTML
    - CSS
    - JavaScript
    - Бэкенда
  answer: 1
  why: HTML дал кнопку, JavaScript — поведение. За внешний вид отвечает CSS.
- q: Вы открыли вкладку Network и обновили страницу. Что вы увидите?
  options:
    - Код сервера
    - Все запросы, которые браузер отправил при загрузке страницы
    - Содержимое базы данных сайта
    - Список открытых вкладок
  answer: 1
  why: Network показывает запросы и ответы. Код сервера и базу данных из браузера не видно — они на сервере.
:::
